# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

**Full rebuild (stop → frontend → backend + plugins → launch):**
```
.\rebuild.bat
```
Or with options:
```powershell
.\rebuild.ps1                  # full rebuild + launch
.\rebuild.ps1 -SkipFrontend    # backend only
.\rebuild.ps1 -SkipBackend     # frontend only
.\rebuild.ps1 -NoLaunch        # build without launching
```

The rebuild script uses the shared `redbamboo-packages/dotnet/rebuild.ps1`. It stops RedCompute.exe, kills WSL backend processes, builds the solution, and launches. Normally you should NOT launch manually: RedCompute is a managed child of the Leaf kernel (RedLeaf), which spawns it (or adopts an already-running instance) — prefer `.\rebuild.ps1 -NoLaunch` and let the kernel start it.

The kernel locates `RedCompute.exe` through the `compute` path in `leaf.workspace.json` (in the `redleaf` repo), which points at this checkout; `src\RedCompute.App\bin\Release\net9.0-windows\RedCompute.exe` is the probed build output. `computeExePath` in the kernel config overrides it.

Tests live in `tests/` (`RedCompute.App.Tests`, `RedCompute.Plugin.Codex.Tests`, `RedCompute.ReleaseTool.Tests`, `RedCompute.NodeLink.Tests`, `RedCompute.Node.Tests`); run them with `dotnet test` and an `--artifacts-path` outside the checkout when a live RedCompute runs from it. `release/Test-LockedRestoreModes.ps1` checks that every committed lock file restores in locked mode. `tests/RedCompute.KernelLinkHarness` is no test project: it is RedCompute's side (NodeHub, node endpoints, kernel sync and a real leaf-node agent) of the kernel's end-to-end revoke test, redleaf's `NodeRevokeEndToEndTests`, which runs it when `LEAF_KERNEL_LINK_HARNESS` names its built executable.

### Linux (preview)

`LeafTargetOs` (in `Directory.Build.props`) selects the host: `windows` builds the unchanged `net9.0-windows` WPF shell and `RedCompute.exe`; `linux` builds a headless `net9.0` console host (`Program.cs`) that maps SIGINT/SIGTERM to the normal shutdown. It defaults to the build machine's OS and follows `-r linux-x64`/`-r win-x64`, so `dotnet publish src/RedCompute.App/RedCompute.App.csproj -c Release -r linux-x64 --self-contained` works from either OS. Linux graphs restore from `packages.linux.lock.json` beside each `packages.lock.json`; regenerate both with `dotnet restore RedCompute.sln --force-evaluate` and again with `-p:LeafTargetOs=linux`. `Directory.Build.rsp` enables Windows targeting so Linux can restore AppHost's `net9.0-windows` TFM.

Off Windows, the WSL/Python GPU providers (TtsLocal, SttLocal, DiarizationLocal, launching ComfyUI or Kev) report `BackendStatus.Unsupported` with a reason instead of spawning `wsl.exe`/`cmd.exe`; tests that need Windows use `[WindowsFact("reason")]`.

## Architecture

RedCompute is a local AI compute orchestrator: a headless .NET 9 service that manages AI backends and exposes a unified REST API on port 18800. It has no frontend of its own — the dashboard is the `compute-dashboard` Leaf plugin, served by the kernel and talking through the kernel's `/compute/*` proxy. It uses a plugin architecture where capabilities and providers are pluggable.

### Projects

- **RedCompute.Core** — Interfaces, models, configuration. No dependencies. Defines `IBackendProvider`, `IPluginProvider`, `JobRequest`/`JobResult`, `CapabilityDefinition`, config classes, discovery models.
- **RedCompute.ExecutionHost** — References Core only. `IExecutionHost` (paths, files, processes, containment, hardware, network of one machine) and node zero's `LocalExecutionHost`, plus `PlatformSupport`. Namespaces stay `RedCompute.PluginSdk.Hosting(.Local)`; PluginSdk forwards the types (`TypeForwards.cs`). The node agent runs this code without ASP.NET Core.
- **RedCompute.NodeLink** — No references. The node link protocol (design: Phase 3): 24-byte frame codec, channels with seq/ack/replay/credit windows, priority scheduler, hello/version negotiation, heartbeat, durable-stream spool, `LinkClient` (node) and `LinkServer` (NodeHub core). `Noise/` is the end-to-end encryption (Phase 4 P0.5): `Noise_IK_P256_AESGCM_SHA256`, the node pinning the server's static key, then one AEAD record per message (counter nonces, never the channel seq). It is wired through `LinkClientOptions.Secure`/`LinkServerOptions.Secure` (null = plaintext), and close codes 4495/4496/4497 put the client in `NeedsRepin`. Senders split at `FrameCodec.MaxSendPayload` so a sealed frame fits the relay's cap. `Forward/` is the port forward (Phase 4 P4, features `forward.http.v1`/`forward.ws.v1`): one HTTP exchange per `port` channel (strict OPEN meta, response head `u32 length + {status, headers}`, a `{bytes, sha256}` trailer on each CLOSE, `forward_truncated` on a mismatch) and one WebSocket per `port.ws` channel; `ForwardClient` is the server side (32 exchanges per runtime and 128 per link, queued on the server), `ForwardHost` the node side over an `IForwardTarget`. `port` and `port.ws` autotune their receive window (`WindowTuner`: 2 x rate x RTT, 8 MiB per channel, 32 MiB per link). Tests in `tests/RedCompute.NodeLink.Tests`, including the fault-injection harness (`NODELINK_FAULT_SEEDS` for long runs).
- **RedCompute.Node** — References NodeLink + ExecutionHost (no ASP.NET Core). The node agent `leaf-node` (one process per OS user): pairing (ECDSA P-256 key in CNG + Credential Manager, the Secret Service via libsecret, or a 0600 file with `--allow-file-key`), the link client (ES256 assertion, `X-Leaf-Node-Error` verdicts), the Phase 3 methods (`node.describe`/`hardware`/`cli`, `diag.echo`) and, with a server that lists them, Phase 4's `runtime.v1` (`runtime.list|start|stop|status`, parameters exactly those members, `runtime.changed` pushed; no `runtime.logs`: a runtime's output stays in its log file on the node) and the `port`/`port.ws` forwards (everything else `method_not_allowed` + the local audit log). Runtimes (P5, `Runtimes/`): only the owner registers them (`leaf-node runtime add comfyui --path … | --attach http://127.0.0.1:<port> --accept-graphs-run-installed-nodes`, then `list|test|enable|disable|remove|start|stop`) in `<data>/runtimes.json`; the server sees id, kind, label, status, accelerator, capabilities and ports, never paths or arguments. A spawned runtime is built from `RuntimeRecipes`, runs `Kept` (state and ledger in `<data>/runtimes/`, re-adopted after an agent restart, identity tracking where containment returns null) and stops on kill-all, revoke, unpair, disable, remove and uninstall; an attached one is only probed and reached. `RuntimeForwardTarget` admits a forward only to a registered, running runtime on its kind's allowlist (`RuntimeRoutes`: path and query decoded strictly and rebuilt; `/view` output|temp only and only the files the server's own prompts produced (`ServerOutputs`: recorded from their `/history/{id}` answers, at most 256 per answer and the latest 4096 per runtime for 24 h, in memory), `/upload/image` parameter rules, no `/object_info`, `BodyGuards` for the upload's multipart (one Content-Type, rebuilt; no preamble or epilogue), a `/prompt` that does not choose its `prompt_id`, `POST /queue` delete-only, `POST /free` exactly `{unload_models?, free_memory?}` booleans and refused `runtime_busy` while the owner's own prompts run or wait (the node reads the runtime's queue itself), and `GET /queue` redacted on the node (`RuntimeAnswers`: each item `[number, id]` for a prompt the server submitted, `[number, "other"]` for the owner's, no graphs or extra data); `/interrupt` (exactly `{prompt_id}`), `/queue` delete, `/api/jobs/{id}/cancel` and `GET /history/{id}` (never `/history` itself) act only on the prompt ids the runtime answered to the server's `/prompt` through this forward, `SubmittedPrompts`), sends `Host: 127.0.0.1:<port>` with `Connection: close`, and drops credentials, forwarding and hop-by-hop headers, revocation cleanup (a pinned node acts only on the server's sealed in-band `link.verdict` or the welcome's refusal; a bare close 4403 or an HTTP 403/404 is `revoked-unverified`, deletes nothing and retries with backoff), end-to-end link encryption (P0.5c: the server link key pinned at pairing from the kernel's `linkKey` and confirmed by a signed proof to `/api/nodes/link/pin`, a link key beside the identity key with the same protection, `leaf-node repin --code` for a node paired before E2E or a changed server key; a pinned node never sends plaintext, and 4495/4496/4497 show `needs-repin`, never a silent re-pin), control IPC (same-user pipe/socket), install/uninstall. It sets `REDCOMPUTE_DATA_ROOT` to its own `compute` folder; `LEAF_NODE_HOME` isolates an agent (tests). Tests in `tests/RedCompute.Node.Tests`. Packaging (R7): publish profiles in `Properties/PublishProfiles` (win-x64, linux-x64; pass `-r` too), the systemd unit template `Install/leaf-node.service` (embedded), and `release/leaf-node/` (the Nightly recipe `Build-LeafNodeArtifacts.ps1`, `leaf-node-install.ps1`, `leaf-node-install.sh`; see `docs/release-component-input.md`). With `LEAF_NODE_HOME` set, `install` records its Run/Uninstall/systemd registrations under `<home>/registrations` instead of writing them.
- **RedCompute.PluginSdk** — References Core + ASP.NET Core. Provides `ICustomEndpointProvider` interface and `ProviderHelpers` utilities for plugin authors.
- **RedCompute.App** — WPF tray app embedding an ASP.NET Core HTTP server. Contains the generic endpoint engine, discovery, registry, and all orchestration logic.
- **plugins/** — Individual provider projects, each implementing `IPluginProvider`. Discovered at runtime via assembly scanning.

### Plugin System

Providers are self-contained .NET projects under `plugins/`. Each implements `IPluginProvider` (from Core) and optionally `ICustomEndpointProvider` (from PluginSdk) for custom API routes. Built-in plugins:

- **RedCompute.Plugin.ComfyUI** — Image/video generation via ComfyUI workflows, WebSocket progress tracking
- **RedCompute.Plugin.Suno** — Cloud music generation via Suno API
- **RedCompute.Plugin.LocalWsl** — Generic HTTP proxy provider (starts process, health-checks, proxies requests)
- **RedCompute.Plugin.TtsLocal** — TTS via Qwen3-TTS (wraps LocalWsl, adds voice discovery)
- **RedCompute.Plugin.SttLocal** — STT via faster-whisper (wraps LocalWsl, adds model/language endpoints)
- **RedCompute.Plugin.ClaudeCode** — AI sessions via Claude Code CLI

**Creating a new provider:** Create a project under `plugins/`, reference `RedCompute.PluginSdk`, implement `IPluginProvider`. The constructor takes `(ProviderConfig config, string capabilitySlug, Action<string> log)`. The `ProviderType` property must match the `Type` field in config.json. At startup, `ProviderDiscovery` scans `{exe}/plugins/*.dll` and registers all `IPluginProvider` implementations.

**Adding a new capability:** Just configure it in `config.json` with a provider. If the provider's `CapabilitySlug` is a slug RedCompute has never seen, it creates the capability automatically. Add a `capabilities/{slug}.json` manifest for display metadata (icon, color, description).

### Capability & Provider System

A **capability** is a type of AI workload identified by a string slug (tts, stt, image-gen, etc.). A **provider** is a specific backend that fulfills a capability. One capability can have multiple providers; one is the active default.

Capabilities are NOT hardcoded — any string slug works. Display metadata (icon, color, name) comes from JSON manifest files in `capabilities/`, overridable by user config.

**Startup flow** (`App.xaml.cs`):
1. Load config from `%LOCALAPPDATA%\RedCompute\config.json` via `ConfigManager`
2. `ProviderDiscovery.ScanAssemblies()` — finds all `IPluginProvider` types from plugins/
3. `InitializeCapabilities()` — iterates config capabilities, creates providers via `ProviderDiscovery`, loads capability metadata via `CapabilityManifestLoader`, registers into `CapabilityRegistry`
4. Start `RelayServer` (ASP.NET Core on port 18800)
5. `ProbeRunningBackends()` — starts all active providers concurrently

**Key services:**
- `ProviderDiscovery` — assembly-scanning provider factory, replaces hardcoded switch
- `CapabilityManifestLoader` — loads capability display metadata from JSON manifests
- `CapabilityRegistry` — maps slug → `CapabilityEntry` (definition + providers + state)
- `JobTrackingService` — SQLite-backed job lifecycle (create/run/complete/fail)

### API Endpoints

`GenericCapabilityEndpoints` registers routes for every registered capability:

- `POST /{slug}/generate` — universal work endpoint. Validates against provider's `InputParameters` schema, calls `ExecuteAsync`, handles sync/async/proxy modes.
- `GET /{slug}/jobs/{id}/output` — retrieve completed output
- `GET /{slug}/jobs/{id}/progress` — real-time progress
- `/{slug}/{**path}` — proxy catch-all for providers with `GetProxyTargetUrl()`

Providers register additional endpoints via `ICustomEndpointProvider.MapCustomEndpoints()` (e.g., `/image-gen/workflows`, `/tts/voices`).

`/discover` manifest and `/openapi.json` are generated from provider-declared `InputParameters` and `OutputSchema` — no manual maintenance needed when adding providers.

Cross-cutting: `/status`, `/jobs`, `/logs`, `/control/start|stop/{slug}`, `/settings`, `/ws` (WebSocket events).

Nodes: `GET /nodes` lists node zero and the remote nodes paired in the kernel, a remote node only to its owner and to admins with a signed subject, as the kernel's `/api/nodes` does (LocalDefault and services see node zero only). One rule, `NodeAccess` (`Services/Nodes/NodeAccess.cs`), decides both seeing a node and placing on it: placement on generate, sessions and execute, `?nodeId=` on `/control/start|stop`, and Automatic routing all go through it. Owner and admins may place, an Agent counts as its person, and the kernel without a person sees every node but places only on node zero. A node the caller may not use answers exactly like an unknown id (404 `node_not_found`), and Automatic picks only node zero or the person's own nodes (identity synced from the kernel's `GET /api/nodes` at boot, every 5 minutes and on `POST /nodes/changed`; liveness from the link), each with `placement {eligible, reason}`. A remote node is eligible (`placement.eligible`) when it is confirmed, not revoked, online and its agent speaks `runtime.v1` and `forward.http.v1` (else the first failing reason; a Phase 3 agent is `needs_update`); `INodeRegistry.HostFor` then gives NodeHub's `RemoteExecutionHost` (P6, `Services/Nodes/RemoteExecutionHost.cs`) and throws `NodeUnavailableException` otherwise. A remote host offers only `Runtimes` (the runtimes its owner registered, over `runtime.v1`; reports from `runtime.list` at link-up and `runtime.changed` pushes, kept in the registry and its cache, capabilities from the server's own kind table `RemoteRuntimeKinds`) and `Network`'s handler and WebSocket over the forward (`ResolveServiceUri` is a `.leaf-node.invalid` sentinel); every other member throws `RemoteOperationNotAllowedException`. `/nodes` lists a remote node's capabilities from its runtimes; `/control/start|stop/{slug}?nodeId=` on an eligible node calls `runtime.start|stop` (node zero's provider untouched); Per-node providers (P7, `Services/Nodes/NodeProviders.cs`): for each runtime a remote node reports, `NodeProviderManager` creates the capability's provider through `ProviderDiscovery` (`RemoteProviderCreation.Create`, called by `RedComputeHost.CreateRemoteProvider`: node zero's constructor services with the node's `RemoteExecutionHost.ForRuntime(id)` and a `NodeScopedAcceleratorAdmission`; `ProviderDiscovery.CreateOnHost` throws unless a constructor receives that host in every execution-host parameter, so a remote provider never falls back to `LocalExecutionHost.Shared`; the scoped admission takes only a remote node id and rewrites every accelerator id to `{node}/{bare}`), under node zero's provider name, in `CapabilityEntry.NodeProviders` (`(provider, nodeId)`; node zero's `Providers` untouched), from an allowlisted config (`RemoteProviderConfig`: type, display name, timeouts, `_`-keys, the runtime's port and accelerator; never paths, `Host`, `WslDistro`, keys or costs). A `RemoteNodeProvider` wraps it: status from the node's report and eligibility (Running only while available), start/stop as `runtime.start|stop`, retired when the node stops reporting the runtime, is forgotten or is revoked (disposed after its running jobs), and RedCompute's shutdown never stops a node's runtime. `/{slug}/generate` with a remote `placement.nodeId` runs that node's provider (`ProviderResolver`: the requested name there, else the active name, else the only one; 422 `provider_unavailable_on_node` with `availableOn` by See; 503 `provider_not_running` with `nodeId` and `reason`, no auto-start); the job records the node, and `/jobs/{id}/rerun` of a remote job names that node (`GlobalEndpoints.RerunBody`), so an offline or gone node is the typed 409/404 a fresh generate gets, never node zero. Automatic stays on node zero (the GPU preference is not in this release). Accelerator gates are per node (`AcceleratorWorkload.NodeId`, null = node zero, unchanged ids); a remote job's cost uses its node's GPU from the last hardware report (`GenericCapabilityEndpoints.RemoteJobCost`; a CPU runtime has none). `/status` adds each capability's `nodes[]` (`{nodeId, provider, status, available, reason, accelerator}`, See-filtered, absent when empty); `capability.status` stays node zero's (the broadcaster cannot filter by See). `/discover/nodes` lists the `placement.nodes.v1` feature concept. `/ai-session/sessions` and `/ai-session/execute` on a remote node stay 422 `provider_unavailable_on_node`. Generate and `/status` for node zero are pinned by `GenerateNodeZeroPinTests` (captured at P6). `/nodes/hub` is NodeHub, the kernel's internal WebSocket hop for node links: it accepts only the kernel's single-use `leaf-node-ingress` execution identity from loopback and is hidden from `/discover`. `404 node_unknown` and `403 node_revoked` are verdicts (the agent deletes its key), so NodeHub answers `node_unknown` only after a kernel read that started after the dial; when the kernel cannot answer it is `503 node_registry_unavailable` with `Retry-After`. A node missing from one `GET /api/nodes` is forgotten locally, never revoked: only the kernel's revoked status or `POST /nodes/{id}/revoked` closes a link with 4403. The last state of each remote node is cached in `<data root>\nodes\<id>.json`. End-to-end link encryption (P0.5, inactive until the kernel's K0): NodeHub answers a node's Noise handshake with RedCompute's link key (`<data root>\node-link-key\current.json`, Durable, DPAPI or 0600; `NodeLinkKeyStore`) and verifies the node's identity binding against RedCompute's own pin of the node's identity key: taken on first use from the `publicKeySpki` the kernel lists, kept in `<data root>\node-trust\<id>.json` (Durable; `NodeTrustStore`, untouched by a forget or a rebuild), never replaced by a later list (that shows `identityPin: conflict`), and cleared only by the owner or an admin in person (`POST /nodes/{id}/identity-pin/reset`). It refuses plaintext from a node the kernel marks `linkE2e: required`, or one whose first encrypted record opened (4496); a replayed message 1 records nothing. A trust record that does not open, or a fault while checking, is 1011 (retry), never a verdict. `GET /nodes` carries RedCompute's own `linkKey` (fingerprint, keyId) once it exists. `GET /nodes/link-key` is the key for the kernel to hand a pairing node (service:redleaf only, hidden from `/discover`). `GET /nodes` shows a remote node's `encryption` (required|none) and `link.encrypted`. `GET /nodes/agent` says where the Nightly published leaf-node (download links, size, SHA-256, install one-liner per OS), read from the public release feed through the RedCompute pointer, record and `leaf-node-manifest.v1.json` (10-minute cache); `available: false` with a reason before a release carries it.

### Frontend

None in this repo. The dashboard is the `compute-dashboard` Leaf plugin (its own repo, `T:\Projects\compute-dashboard`), served by the Leaf kernel; it reaches this service through the kernel's `/compute/*` proxy.

### Database

SQLite via Entity Framework Core. `RedComputeDbContext` in `RedCompute.App/Data/`. Stores jobs and logs. Schema managed by `EnsureCreated()` + `MigrateSchema()`.

### Configuration

`%LOCALAPPDATA%\RedCompute\config.json`. Structure: `RedComputeConfig` → `Capabilities` (dict of slug → `CapabilityConfig` → `Providers` dict of name → `ProviderConfig`). `ProviderConfig.Type` matches a provider's `ProviderType` property. `ProviderConfig.Extra` (JsonExtensionData) holds per-provider flexible settings. Display overrides (`DisplayName`, `Icon`, `Color`) can be set in `CapabilityConfig`. Editable via `/settings` API endpoints or direct file edit.

**Stored paths and moves.** Writers still store absolute paths (`Jobs.OutputLocation`, `InputAttachments.StoredPath`, long-lived `logPath`/`workingDirectory`), because a rolled-back build reads them as absolute; readers also accept a relative value (`StoredPaths.Resolve` against `ComputeStorage.Outputs`, `InputAttachments` or the data root), so a later release can switch writers once a minimum version is pinned. `config.json` does not persist RedCompute's own install directory (`backends\<slug>`) for the providers the defaults fill in. When the kernel moves data it sets `REDCOMPUTE_REBASE_MAP` (`{ generation, map: [{from,to}] }`; malformed = exit 78). At startup, before any store opens, `StoredPathRebaseRunner` runs every rebaser (`src/RedCompute.App/Rebase/`: job outputs, attachments, the Claude/Codex/OpenCode session databases, long-lived processes, config) once per generation, records the completed generation in `<data root>\rebase-state.json`, and `GET /storage/rebase-status` reports `{ generation, state: pending|running|completed|failed, owners }`. A rebaser rewrites an absolute value under a `from` folder to the same absolute value under its `to` folder. Values outside every `from` folder are never touched; a failed owner is retried at the next start.

Capability display metadata: `capabilities/{slug}.json` files with `displayName`, `description`, `icon` (FontAwesome class), `color` (hex), `category`. Shipped manifests in repo root `capabilities/`, user overrides in `%LOCALAPPDATA%\RedCompute\capabilities/`.
